orc-review: model-planned code review workflows on the orc runtime

The complete engine design as implemented. orc-review owns exactly three things — creation, running, and monitoring of one review workflow — plus a rendered verdict. Publication, humans, webhooks, and PR lineage belong to a future service layer that embeds this engine.

1 · The pipeline: law → craft → law

Deterministic logic decides who reviews and whether the result can be trusted; a model decides how the review runs. Every model output crosses a deterministic gate before it matters.

2 · The change under review: repo sets

A review always runs over a set of repo pins, N ≥ 1. There is no single-repo vs multi-repo mode anywhere in the engine — one repo is a set of size one. The caller names the set; nothing is structurally discovered. This covers the plain case (orc-review run in a checkout), the migration case (a library and its consumer reviewed together), and anything a custom source can materialize. 

orc-review run                                          # {git: "."} — one pin
orc-review run --repo app=~/code/app@origin/main \
               --repo lib=~/code/lib@origin/main        # a two-repo migration review
orc-review run --repo github:acme/lib#412               # custom source, scheme-routed

RepoPin — one repository's pinned change

interface RepoPin {
  id: string;            // caller alias (default: basename) — namespaces paths, bots, lanes
  root: string;          // local checkout the lanes read
  baseLabel: string;     // what was asked for ("origin/main")
  baseSha: string;       // resolved merge-base — pinned SHA, never a branch name
  headSha: string;
  fingerprint: string;   // HEAD + index/worktree diff + untracked contents digest
  dirty: boolean;
  untracked: string[];
  changedPaths: string[];  // repo-relative (selection facts for this pin)
  diffBriefing: string;    // how an agent views this repo's change
  configTree: Tree;        // trusted side for this repo's .orc-review (base tree)
  headTree: Tree;
}

RepoSource — the extension seam

A source's whole job: materialize one repo's change locally and pin it. git (a local checkout) is built in; custom sources (a GitHub PR fetcher, an internal VCS) register in orc-review.config.(mjs|js) — the single explicit extension point, no ambient scanning — and are addressed by scheme (github:acme/lib#412). Source selection is caller-side, never in the reviewed manifest (the source determines where the manifest comes from). An optional refresh(pin) re-fingerprints for staleness (monotonic; reserved for the service layer).

Dirty reviews are first-class

  • The change under review is base → worktree: uncommitted and untracked work is included, both in selection facts and in what lanes are briefed to diff.
  • Briefs pin the merge-base SHA, so a base branch moving mid-review cannot skew lanes; dirty pins are briefed git diff <baseSha> with untracked files listed explicitly.
  • Attempt identity is the changeId: for one pin, headSha or headSha12+fingerprint12; for a set, set-<digest16>[+dirty] over the ordered pin fingerprints. Same HEAD, different uncommitted edits → different attempts, different plan files. The rendered header carries +dirty.

The composed workspace

Lanes run read-only in ~/.orc-review/workspaces/<changeId>/ — a directory of symlinks, one per pin, named by id. Uniform for N = 1. Agents address everything as <repoId>/<path>; findings must anchor paths the same way (enforced by the schema description and the brief), which is what makes inline-comment anchoring work against the composed changed-path set.

Uncovered repos

A pin whose base tree has no .orc-review fails the run by default — silently reviewing half a migration is the one truly bad outcome. --allow-uncovered opts into skipping it, rendered as a warning, and deterministically forces the verdict to PARTIAL — NOT APPROVED: unjudged changes never approve.

3 · Configuration & reviewer authoring

Config is repository-owned and trusted only from the base tree (git show <base>:.orc-review/…) — a PR cannot alter its own reviewers. Closed schema throughout: unknown fields rejected, confined paths, no symlinks, one YAML document, 256 KiB manifest cap, unique ids, rules must reference known reviewers. 

.orc-review/
├── manifest.yaml
└── reviewers/
    ├── security.md          # simple reviewer: frontmatter + prompt
    └── abhinav/             # composite reviewer
        ├── reviewer.yaml
        └── prompts/*.md
# manifest.yaml
version: 1
reviewers:
  - id: security
    source: reviewers/security.md      # required: true is the default
  - id: abhinav
    source: reviewers/abhinav
selection:
  always: [security]
  rules:
    - id: backend
      when: { any_changed_path: ["**/*.go", "src/**"] }
      add: [abhinav]
run:
  budget: 5                    # reactive USD cap for the whole run
  max_parallel: 8
  aggregator_model: gpt-5.6-sol       # defaults shown; harness/effort too
  aggregator_harness: codex
planner:
  model: claude-fable-5        # or disabled: true → template only

Simple reviewer — one markdown file:

---
model: claude-sonnet-5
can_block: true            # authority bits live here and in the manifest — never elsewhere
---
You are the security reviewer. Hunt for injection, authz, and secret-handling defects.

Composite reviewer — several lanes plus the bot's adjudication voice:

# reviewers/abhinav/reviewer.yaml
display_name: Abhinav
can_block: true
verbatim: false                        # true = never merged, models untouched
lanes:
  - { prompt: prompts/correctness.md, model: claude-opus-4-8 }
  - { prompt: prompts/tests.md,       model: claude-sonnet-5 }
aggregation_notes: prompts/adjudicate.md   # injected into the aggregator, attributed
                                           # (rev 1's `synthesis:` accepted as alias)

From the outside a bot is atomic — one id, selected, excluded, required, attributed as a unit. Its lanes run in the flat layer; there is no per-bot synthesis stage. In a repo set, every bot and lane is namespaced by pin id: bot app/security, lane app/security/prompt, display "Security (app)".

4 · The local bot registry

Personal bots live once in ~/.orc-review/registry/ (same authoring formats) and are called onto any run with --with <name>. Registry bots are advisory by construction: required/can_block only ever come from a reviewed repo's own manifest, so local bots are forced to required: false, can_block: false regardless of what their files claim — the deterministic severity cap (§10) enforces it downstream. They are labeled "(local)" in attribution and provenance, excluded from Reviewer-Change classification, and cannot shadow a repo-defined reviewer id. orc-review bots lists the registry. A repo that wants a personal bot as a merge gate defines it in its own .orc-review like any reviewer.

5 · Selection & eligibility law

Both run per repo, with repo-relative facts — manifests never see namespacing. Deterministic to the byte for identical inputs:

  • Selection is the accumulative, order-independent union always ∪ additions from every matching rule ∪ eligible affinity — no remove, no first-match, no last-writer-wins. Sorted by manifest declaration order; per-bot reasons (always, rule:<id>, affinity). The only inputs are selection facts (changed paths); PR titles, authors, labels, clocks, and model judgment are deliberately absent.
  • Globs: ** spans any number of path segments; other segments use Go path.Match semantics (*, ?, […]). Purely lexical.
  • Reviewer Change: any changed path under .orc-review/ in any pin. Changed bots (content hash at base ≠ head) are excluded from execution; an uncompilable head config marks every selected bot changed (fail closed). Any Reviewer Change caps the whole run's verdict at ADVISORY.

6 · Planning: the flat lane layer craft

A planner model (default claude-fable-5 via the claude CLI, pluggable) authors the literal orc program. The execution shape is fixed — flat, depth 1: the union of every eligible bot's lanes runs as one concurrent layer; exactly one aggregation stage consolidates. Within that shape, the planner's craft is:

  • Lane merging — the planner's whole craft: lanes from different bots pursuing the same mandate (two security reviews, two test-run lanes — including across repos in a set) merge into one execution. A merged prompt concatenates each key's verbatim text — never paraphrases; the strongest declared model wins; the settled status reports under every constituent key; findings attribute to the union of bots. verbatim: true bots are exempt. When in doubt, don't merge.
  • No support tier. Every agent call in the program is a judgment lane or the aggregator — nothing else. A bot that wants extra work (running the test suite, cataloging APIs) declares it as a lane, and lanes do their own legwork with their own tools; when several bots want the same work, merging is what deduplicates it. The planner may append CTX facts after (never instead of) a lane's verbatim text.

Judgment text is verbatim by construction: prompt bodies are injected into the program header as PROMPTS constants and the planner only ever references them — it never holds the text. Rejected programs retry once with verifier feedback; the final fallback is a deterministic template generator (every lane independent, no merges, no merges) that passes verification by construction. The program returns { consolidated, laneOutcomes }.

7 · Verification law

The planner proposes; a TypeScript-AST verifier disposes. Checked structurally on the assembled program:

RuleEnforced as
Lane coverageEvery lane key of every eligible bot appears exactly once across tier 1; one call may carry several keys (a merged lane)
Verbatim judgmentEvery prompt referencing PROMPTS must start with a PROMPTS[…] reference; string-literal keys only
Verbatim botsTheir keys sit in single-key calls — never merged
SchemasJudgment calls carry SCHEMAS.findings
No support tierEvery agent call is a judgment lane or the aggregator; any free-prompt call is rejected
AggregationExactly one call with SCHEMAS.consolidated, prompt headed by MERGE_PROMPT, zero PROMPTS references
EscapesNo readOnly/cwd/host options, no ext, no redeclaring injected constants, phase names are string literals

Then orc's own validate compiles the program in the deterministic sandbox, previews the first frontier, and live-probes every referenced harness/model/effort. Lane isolation ("no lane's output in another lane's prompt") is stated to the planner but needs data-flow analysis to prove; the structural rules plus read-only leaves bound the blast radius of a violation.

8 · Execution on orc

One orc run per attempt: the pinned program bundle (sha256 recorded) is the review spec, the journal is the evidence trail, and orc's live monitor is the review UI — phase cards (review / aggregate), per-lane rows with harness · model · cost · duration, a self-contained report.html. Launch parameters: cwd = the composed workspace, approvalMode: auto, allowWrites: false (every leaf read-only, fail-closed), budget/maxParallel from the primary manifest or flags. The brief injected into every leaf enumerates each repo's pinned diff instructions and the path-addressing convention. Lane failures settle as envelopes; one failing lane never sinks the run. Fail-forward resume and replay come from orc.

9 · The aggregator craft

The single depth-1 consolidation stage — the only place findings merge. Default model: gpt-5.6-sol on the codex harness (run.aggregator_model/harness/effort to override). Inputs: every lane's settled envelope labeled by key(s), the bot roster (ids, display names, authority bits, lane keys), per-bot aggregation_notes, and the change facts. Its mandate — deliberately stronger than any single bot's:

  • Same defect, any wording → one finding: worst source severity, union of sourcing bot ids.
  • Symptom chains collapse into their cause; the symptoms fold into its rationale.
  • The same defect at N sites → one finding enumerating the sites.
  • Adjacent nits about the same hunk coalesce.
  • Discipline: disagreement downgrades exactly one severity rank, never below nit; a blocking finding is never dropped except by merging into another blocking finding; nothing is invented that no lane reported.
  • Failure honesty: every errored lane becomes an omission; only if every lane errored is readiness forced to unknown — otherwise it judges from the lanes that succeeded.
  • Bot voice: a bot's aggregation_notes govern findings sourced only from its lanes and weigh in cross-bot merges.

10 · Verdict, completeness, rendering law

The aggregator's output is evidence, not authority — a deterministic pass decides what it can mean. Malformed or missing results parse to null and fail closed.

Deterministic ruleEffect
Lane failure semanticsA failed (or unreported) lane degrades coverage — noted in the review, not fatal. A bot is complete iff at least one of its lanes settled ok.
Completenessrun completed ∧ result parses ∧ every required bot has ≥1 surviving lane ∧ no uncovered repos ∧ readiness ≠ unknown
Authority capA blocking finding survives only if some sourcing bot has can_block; otherwise deterministically capped to SHOULD FIX (noted). Merged findings pass if any contributing bot can block.
PriorityConditionVerdictAction hint
1Empty cohortABSTAINEDCOMMENT
2Surviving blocking findingCHANGES REQUESTEDREQUEST_CHANGES
3Not completePARTIAL — NOT APPROVEDCOMMENT
4Reviewer ChangeADVISORY — AUTOMATION CLEAREDCOMMENT

6OtherwiseREVIEWEDCOMMENT

The rendered Consolidated Review: header (orc-review · VERDICT · <changeId7>[+dirty]), Reviewed-by, coverage, summary, warnings (reviewer change, uncovered repos, incomplete, degraded lane coverage, capped severities), findings sorted by severity rank with MUST FIX / SHOULD FIX / CONSIDER / NIT counts, per-finding why/fix/attribution, omissions, and a collapsible run-details block. Inline-comment anchors are computed for findings on changed files (for a future publisher) but every finding also stays in the body. A clean approval says exactly "No findings survived scrutiny." — never padded.

Provenance (run details)

Every review records: orc run id, per-repo pins (base (sha) → head[+dirty]), plan origin + program sha256, aggregator harness · model, per-bot content hashes (local bots marked), monitor URL, report path. "Which bots, at which content, reviewed which pinned change, under which plan" is always answerable from the output alone.

11 · CLI & library surfaces

orc-review validate                    # working-tree config check
orc-review plan [--repo …]             # per-repo cohort, reasons, lanes — instant, no model
orc-review plan --program              # …plus the planner-authored program (verifier-gated)
orc-review run  [--repo …] [--with bot] [--budget N] [--allow-uncovered] [--open] [--json]
orc-review bots                        # list the local registry
# global: --dir/--base (single-repo sugar) · --repo [id=][scheme:]spec[@base] (repeatable)
import { prepare, execute, review } from "orc-review";
const outcome = await review({ repos: ["app=.", "lib=../lib@origin/main"] });
outcome.evaluation.verdict;      // "APPROVED" | …
outcome.rendered.body;           // Consolidated Review markdown
outcome.rendered.inlineComments; // anchored findings for a future publisher
outcome.monitorUrl;              // live monitor

prepare() alone is the deterministic half (pins, cohort, classification, generated program) with no launch — the seam a service layer builds on. --json everywhere.

12 · Invariants

A Reviewer Change is never approved by automation. Advisory at best; a PR cannot nominate or alter its own reviewers (config trusted only from base trees).

Selection is deterministic. The planner chooses how reviewers run, never whether. Byte-identical cohorts for identical inputs.

Judgment is verbatim. Prompt text is injected, never model-rewritten; merging is concatenation with union attribution; there is no support tier — every call is a judgment lane or the aggregator.

Depth is exactly 1. Lanes produce findings; one aggregator merges them; nothing else merges judgment. Reviewers never see each other's output.

Authority is repo-granted. required/can_block bind only in a reviewed repo's base-tree manifest — never from the registry, a flag, or a lane.

Fail closed, degrade honestly. Malformed results, failed required bots, uncovered repos, unknown readiness → never approve. Partial lane failures degrade coverage and say so.

Everything reviews read-only from pinned state. SHAs not branch names; dirty state fingerprinted into the attempt identity; no leaf may write.

14 · Deferred: the service layer

Explicitly out of engine scope, designed to compose around prepare()/execute() and the rendered output: GitHub publication (action hints and inline anchors are already computed), PR lineage/supersession and debounce, webhook ingest and reconciliation, human-review roles/SLAs/ Slack, staleness refresh via RepoSource.refresh (monotonic; verdict string STALE — NOT APPROVED reserved), reviewer affinity, and repo enrollment.
