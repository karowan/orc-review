orc-review · architecture and behavior

orc-review: model-planned code review workflows on the orc runtime

orc-review creates, runs, and monitors model-assisted code review workflows on the orc runtime. It selects a repository-defined reviewer cohort, produces a verified execution plan, runs the review, and returns a consolidated verdict with complete provenance.

1 · The pipeline: deterministic → model-planned → deterministic

Deterministic logic decides who reviews and whether the result can be trusted; a model decides how the review runs. Every model output crosses a deterministic gate before it matters.

2 · The change under review: repo sets

A review accepts one or more pinned repositories. Running orc-review run in a checkout reviews that repository; repeated --repo options review related changes together. The caller supplies the repositories explicitly, and custom sources can materialize additional repository types. 

orc-review run                                          # {git: "."} — one pin
orc-review run --repo app=~/code/app@origin/main \
               --repo lib=~/code/lib@origin/main        # a two-repo migration review
orc-review run --repo github:acme/lib#412               # custom source, scheme-routed

RepoPin — one repository's pinned change

interface RepoPin {
  id: string;            // caller alias (default: basename) — namespaces paths, bots, lanes
  root: string;          // local checkout the lanes read
  baseLabel: string;     // what was asked for ("origin/main")
  baseSha: string;       // resolved merge-base — pinned SHA, never a branch name
  headSha: string;
  fingerprint: string;   // HEAD + index/worktree diff + untracked contents digest
  dirty: boolean;
  untracked: string[];
  changedPaths: string[];  // repo-relative (selection facts for this pin)
  diffBriefing: string;    // how an agent views this repo's change
  configTree: Tree;        // trusted side for this repo's .orc-review (base tree)
  headTree: Tree;
}

RepoSource — the extension seam

A source's whole job: materialize one repo's change locally and pin it. git (a local checkout) is built in; custom sources (a GitHub PR fetcher or another VCS) register in orc-review.config.(mjs|js) — the single explicit extension point, no ambient scanning — and are addressed by scheme (github:acme/lib#412). Source selection is caller-side, never in the reviewed manifest (the source determines where the manifest comes from). An optional refresh(pin) re-fingerprints the materialized change so a coordinator can detect staleness before acting on a result.

Dirty reviews are first-class

  • The change under review is base → worktree: uncommitted and untracked work is included, both in selection facts and in what lanes are briefed to diff.
  • Briefs pin the merge-base SHA, so a base branch moving mid-review cannot skew lanes; dirty pins are briefed git diff <baseSha> with untracked files listed explicitly.
  • Attempt identity is the changeId: for one pin, headSha or headSha12+fingerprint12; for a set, set-<digest16>[+dirty] over the ordered pin fingerprints. Same HEAD, different uncommitted edits → different attempts, different plan files. The rendered header carries +dirty.

The composed workspace

Lanes run sandboxed in ~/.orc-review/workspaces/<changeId>/ — a directory of symlinks, one per pin, named by id. Uniform for N = 1. Agents address everything as <repoId>/<path>; findings must anchor paths the same way (enforced by the schema description and the brief), which is what makes inline-comment anchoring work against the composed changed-path set.

Uncovered repos

A pin whose base tree has no .orc-review fails the run by default. This guarantees that every submitted repository is covered by review policy. --allow-uncovered opts into skipping it, renders a warning, and deterministically forces the verdict to PARTIAL — NOT APPROVED: unjudged changes never approve.

3 · Configuration & reviewer authoring

Config is repository-owned and trusted only from the base tree (git show <base>:.orc-review/…) — a PR cannot alter its own reviewers. Closed schema throughout: unknown fields rejected, confined paths, no symlinks, one YAML document, 256 KiB manifest cap, unique ids, rules must reference known reviewers. 

.orc-review/
├── manifest.yaml
└── reviewers/
    ├── security.md          # simple reviewer: frontmatter + prompt
    └── quality-team/        # composite reviewer
        ├── reviewer.yaml
        └── prompts/*.md
# manifest.yaml
version: 1
reviewers:
  - id: security
    source: reviewers/security.md      # required: true is the default
  - id: quality-team
    source: reviewers/quality-team
selection:
  always: [security]
  rules:
    - id: backend
      when: { any_changed_path: ["**/*.go", "src/**"] }
      add: [quality-team]
model_policy:
  allowed:                      # exact, fail-closed tuples
    - { harness: codex, model: gpt-5.6-sol, effort: medium }
    - { harness: codex, model: gpt-5.6-sol, effort: high }
    - { harness: claude, model: "claude-opus-4-8[1m]", effort: max }
  preferences:                  # optional planner guidance matrix
    - harness: codex
      model: gpt-5.6-sol
      effort: medium
      metadata:
        speed: very_fast
        cost: low
        intelligence: high
        guidance: default for broad merged review packets
run:
  budget: 5                    # reactive USD cap for the whole run
  max_parallel: 8
  aggregator_model: gpt-5.6-sol       # defaults shown; harness/effort too
  aggregator_harness: codex
planner:
  harness: codex
  model: gpt-5.6-sol
  effort: medium
  max_calls: 6
  required: true               # no unoptimized fallback may exceed max_calls
  # disabled: true             # alternative: deterministic template only

model_policy.allowed is optional. When present, it constrains the configured planner, reviewer declarations, aggregator, and the planner's final physical judgment calls to exact harness/model/effort tuples. Validation fails closed: an omitted field or a planner-selected tuple outside the list is rejected before execution. The planner still decides how compatible lanes are packed; it cannot escape the repository's model boundary while doing so. preferences is a matrix over a subset of allowed. Every row carries a non-empty, open-ended metadata map. Keys such as speed, cost, and intelligence are conventions rather than engine semantics; the complete matrix is serialized into the planner prompt without interpretation. Preference metadata grants no additional execution permission.

Simple reviewer — one markdown file:

---
model: claude-sonnet-5
can_block: true            # reviewer authority metadata; evidence remains separate from publication
---
You are the security reviewer. Hunt for injection, authz, and secret-handling defects.

Composite reviewer — several lanes plus the bot's adjudication voice:

# reviewers/quality-team/reviewer.yaml
display_name: Quality Team
can_block: true
verbatim: false                        # true = never merged, models untouched
lanes:
  - { prompt: prompts/correctness.md, model: claude-opus-4-8 }
  - { prompt: prompts/tests.md,       model: claude-sonnet-5 }
aggregation_notes: prompts/adjudicate.md   # injected into the aggregator and attributed

From the outside a bot is atomic — one id, selected, excluded, required, attributed as a unit. Its lanes run in the flat layer; there is no per-bot synthesis stage. In a repo set, every bot and lane is namespaced by pin id: bot app/security, lane app/security/prompt, display "Security (app)".

4 · The local bot registry

Personal bots live once in ~/.orc-review/registry/ (same authoring formats) and are called onto any run with --with <name>. Registry bots are advisory by construction: required/can_block only ever come from a reviewed repo's own manifest, so local bots are forced to required: false, can_block: false regardless of what their files claim. This does not rewrite their evidence: a local bot's blocking finding remains blocking and the engine still computes the full dry-run conclusion. A publisher independently limits the side effects it is allowed to perform. Local bots are labeled "(local)" in attribution and provenance, excluded from Reviewer-Change classification, and cannot shadow a repo-defined reviewer id. orc-review bots lists the registry. A repo that wants a personal bot as a merge gate defines it in its own .orc-review like any reviewer.

5 · Selection & eligibility deterministic

Both run per repo, with repo-relative facts — manifests never see namespacing. Deterministic to the byte for identical inputs:

  • Selection is the accumulative, order-independent union always ∪ additions from every matching rule ∪ eligible affinity — no remove, no first-match, no last-writer-wins. Sorted by manifest declaration order; per-bot reasons (always, rule:<id>, affinity). The only inputs are selection facts (changed paths); PR titles, authors, labels, clocks, and model judgment are deliberately absent.
  • Globs: ** spans any number of path segments; other segments use Go path.Match semantics (*, ?, […]). Purely lexical.
  • Reviewer Change: any changed path under .orc-review/ in any pin. Changed bots (content hash at base ≠ head) are excluded from execution; an uncompilable head config marks every selected bot changed (fail closed). Any Reviewer Change caps the whole run's verdict at ADVISORY.

6 · Governor & corroborator routing deterministic

Each path rule adds the reviewer responsible for an area and any corroborating reviewers needed for that work. selection.always supplies the general fallback governor. Governor and corroborator are manifest-authoring roles implemented through deterministic selection rules; models do not infer or modify authority. The selected cohort and reasons are visible in plan output. 

# A repository-owned council
version: 1
reviewers:
  - { id: general,  source: reviewers/general.md, required: true }
  - { id: backend,  source: reviewers/backend,    required: true }
  - { id: product,  source: reviewers/product,    required: false }
  - { id: security, source: reviewers/security,   required: false }

selection:
  always: [general]                 # general governor / fallback
  rules:
    - id: backend-infrastructure
      when:
        any_changed_path:
          - "services/api/**"
          - "infrastructure/**"
          - ".github/workflows/**"
      add: [backend, security]        # area governor + corroborator
    - id: product-experience
      when:
        any_changed_path:
          - "apps/web/**"
          - "apps/mobile/**"
          - "packages/design-system/**"
      add: [product, security]        # area governor + corroborator

This gives every change at least the fallback governor; matching areas accumulate their own governor and peers. A change spanning backend and product receives the union, never one branch chosen at the expense of another. required is deliberately separate from selection: it means a selected bot must retain at least one successful lane for the run to be complete. It does not make that bot run when no rule selected it.

Models never choose review authority. Repository rules choose the cohort from changed paths. The planner may combine selected work, but cannot add, remove, or replace a governor.

7 · Planning: the flat lane layer model-planned

A planner model (default claude-fable-5 via the claude CLI, pluggable) authors the literal orc program. The execution shape is fixed — flat, depth 1: the union of every eligible bot's lanes runs as one concurrent layer; exactly one aggregation stage consolidates. Within that shape, the planner can optimize execution through:

  • Lane merging: lanes from different bots pursuing the same mandate (two security reviews, two test-run lanes — including across repos in a set) merge into one execution. A merged prompt concatenates each key's verbatim text — never paraphrases; the strongest declared model wins; the settled status reports under every constituent key; findings attribute to the union of bots. verbatim: true bots are exempt. When in doubt, don't merge.
  • Execution calls. Every agent call in the program is a judgment lane or the aggregator. A bot that wants extra work (running the test suite, cataloging APIs) declares it as a lane, and lanes do their own legwork with their own tools; when several bots want the same work, merging is what deduplicates it. The planner may append CTX facts after (never instead of) a lane's verbatim text.

Judgment text is verbatim by construction: prompt bodies are injected into the program header as PROMPTS constants and the planner only ever references them — it never holds the text. Rejected programs retry once with verifier feedback. If the manifest sets planner.required: true, two rejected/failed attempts abort the review; otherwise the final fallback is a deterministic template generator (every lane independent, no merging) that passes verification by construction. A configured planner.max_calls is a hard judgment-call ceiling and therefore requires the planner to be required: an unoptimized fallback is not allowed to evade the budget. The program returns { consolidated, laneOutcomes }.

Saved plans

plan --program --json emits a reusable plan artifact. A later run --plan-file does not plan again: it re-resolves the change and reviewer files, binds the artifact to the exact change, cohort, models, aggregator policy, call ceiling, source, and digest, then runs that verified program or rejects it as stale. This is the seam used by a coordinator that wants planning and long-running execution in separate durable steps.

8 · Verification deterministic

A TypeScript-AST verifier checks the assembled program before execution:

RuleEnforced as
Lane coverageEvery lane key of every eligible bot appears exactly once across tier 1; one call may carry several keys (a merged lane)
Verbatim judgmentEvery prompt referencing PROMPTS must start with a PROMPTS[…] reference; string-literal keys only
Verbatim botsTheir keys sit in single-key calls — never merged
SchemasJudgment calls carry SCHEMAS.findings and explicitly set readOnly: false so tests can create artifacts
Call rolesEvery agent call is a judgment lane or the aggregator; any free-prompt call is rejected
AggregationExactly one call with SCHEMAS.consolidated, prompt headed by MERGE_PROMPT, zero PROMPTS references
EscapesNo cwd/host options, no ext, no redeclaring injected constants, phase names are string literals

Then orc's own validate compiles the program in the deterministic sandbox, previews the first frontier, and live-probes every referenced harness/model/effort. Lane isolation ("no lane's output in another lane's prompt") is stated to the planner but needs data-flow analysis to prove; the structural rules still prevent direct cross-lane prompt references.

9 · Execution on orc

One orc run per attempt: the pinned program bundle (sha256 recorded) is the review spec, the journal is the evidence trail, and orc's live monitor is the review UI — phase cards (review / aggregate), per-lane rows with harness · model · cost · duration, a self-contained report.html. Launch parameters: cwd = the composed workspace, approvalMode: auto, allowWrites: true, sandboxed to the pinned roots. Outbound network access is off by default and can be enabled explicitly with run --network (or library option networkAccess: true) without removing filesystem confinement. Reviewer leaves may create test/build/cache/temp artifacts but are briefed not to alter tracked source, commit, push, publish, or change anything outside the workspace; the aggregator stays read-only. Common tool caches are redirected under the composed workspace. Budget and maximum parallelism come from the primary manifest or flags. The brief injected into every leaf enumerates each repo's pinned diff instructions and the path-addressing convention. A bounded --context-file lets a trusted coordinator supply remote checks and metadata once to all lanes without giving them publication credentials. Lane failures settle as envelopes; one failing lane never sinks the run. Fail-forward resume and replay come from orc.

10 · The aggregator model

The single depth-1 consolidation stage — the only place findings merge. Default model: gpt-5.6-sol on the codex harness (run.aggregator_model/harness/effort to override). Inputs: every lane's settled envelope labeled by key(s), the bot roster (ids, display names, authority bits, lane keys), per-bot aggregation_notes, and the change facts. Its mandate — deliberately stronger than any single bot's:

  • Same defect, any wording → one finding: worst source severity, union of sourcing bot ids.
  • Symptom chains collapse into their cause; the symptoms fold into its rationale.
  • The same defect at N sites → one finding enumerating the sites.
  • Adjacent nits about the same hunk coalesce.
  • Discipline: disagreement downgrades exactly one severity rank, never below nit; a blocking finding is never dropped except by merging into another blocking finding; nothing is invented that no lane reported.
  • Failure honesty: every errored lane becomes an omission; only if every lane errored is readiness forced to unknown — otherwise it judges from the lanes that succeeded.
  • Omission taxonomy is closed: lane_failure, test_not_run, external_context, and evidence_gap. Native causes survive; an inapplicable surface is not an omission.
  • Bot voice: a bot's aggregation_notes govern findings sourced only from its lanes and weigh in cross-bot merges.

11 · Verdict, completeness, rendering deterministic

The aggregator's output is evidence, not authority — a deterministic pass decides what it can mean. Malformed or missing results parse to null and fail closed.

The rendered Consolidated Review: header (orc-review · VERDICT · <changeId7>[+dirty]), Reviewed-by, coverage, summary, warnings (reviewer change, uncovered repos, incomplete, degraded lane coverage), findings sorted by severity rank with MUST FIX / SHOULD FIX / CONSIDER / NIT counts, per-finding why/fix/attribution, omissions, and a collapsible run-details block. Inline-comment anchors are computed for findings on changed files for publication integrations, but every finding also stays in the body. Before rendering, finding paths are normalized at the trusted engine boundary: disposable repo prefixes and absolute in-repo paths become stable repository paths; locations outside registered roots lose their anchor rather than pointing somewhere misleading. A clean approval says exactly "No findings survived scrutiny." — never padded.

Provenance (run details)

Every review records: orc run id, per-repo pins (base (sha) → head[+dirty]), plan origin + program sha256, aggregator harness · model, per-bot content hashes (local bots marked), monitor URL, report path. "Which bots, at which content, reviewed which pinned change, under which plan" is always answerable from the output alone.

12 · CLI & library surfaces

orc-review validate                    # working-tree config check
orc-review plan [--repo …]             # per-repo cohort, reasons, lanes — instant, no model
orc-review plan --program --json       # …plus a durable verifier-gated plan artifact
orc-review run  [--repo …] [--plan-file plan.json] [--with bot] [--budget N]
                [--network] [--allow-uncovered] [--open] [--json]
orc-review bots                        # list the local registry
# global: --dir/--base (local checkout defaults) · --context-file evidence.json
#         --repo [id=][scheme:]spec[@base] (repeatable)
import { prepare, execute, review } from "orc-review";
const outcome = await review({
  repos: ["app=.", "lib=../lib@origin/main"],
  networkAccess: false, // default; true retains the filesystem sandbox
  context: trustedCoordinatorEvidence,
});
outcome.evaluation.verdict;      // "APPROVED" | …
outcome.rendered.body;           // Consolidated Review markdown
outcome.rendered.inlineComments; // anchored findings for publication integrations
outcome.monitorUrl;              // live monitor

prepare() alone is the deterministic half (pins, cohort, classification, generated program) with no launch, suitable for coordinators that separate preparation from execution. --json is available throughout the CLI.

13 · Invariants

A Reviewer Change is never approved by automation. Advisory at best; a PR cannot nominate or alter its own reviewers (config trusted only from base trees).

Selection is deterministic. The planner chooses how reviewers run, never whether. Byte-identical cohorts for identical inputs.

Network is explicit. Filesystem confinement is always retained; outbound access is disabled unless the caller opts in for reviews that need external documentation or tool verification.

Judgment is verbatim. Prompt text is injected, never model-rewritten; merging is concatenation with union attribution; every call is a judgment lane or the aggregator.

Depth is exactly 1. Lanes produce findings; one aggregator merges them; nothing else merges judgment. Reviewers never see each other's output.

Evidence is not authority. Reviewers retain their finding severities and full verdict conclusions. Publication integrations enforce their own permissions; registry bots remain non-required and cannot grant authority to themselves.

Fail closed, degrade honestly. Malformed results, failed required bots, uncovered repos, unknown readiness → never approve. Partial lane failures degrade coverage and say so.

Everything reviews sandboxed pinned state. SHAs not branch names; dirty state fingerprinted into the attempt identity; reviewer writes are limited to local test/build artifacts and never grant publication authority.

14 · Integration boundaries

orc-review produces a complete review result but does not publish it. Integrations may consume the rendered body, action hint, inline anchors, provenance, and monitor URL to implement code-hosting comments, notifications, or human-review processes. Those integrations own credentials, publication permissions, event handling, and repository enrollment.

prepare(), execute(), saved plan artifacts, and RepoSource.refresh() provide the boundaries needed to separate deterministic preparation, durable execution, staleness checks, and publication without exposing those responsibilities to reviewer lanes.
